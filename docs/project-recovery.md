# Project recovery and import boundaries

Project exports use a versioned envelope. The top-level collections describe the active scenario named by `meta.scenario`; `scenarioData` contains complete snapshots for every scenario in the export, including the active scenario. `meta.scenarios` is the authoritative scenario registry, and scenario identifiers must match the storage rule `[A-Za-z0-9_-]{1,64}`. If the active scenario is also present in `scenarioData`, the top-level active snapshot remains authoritative and the duplicate is ignored.

The import preview validates the complete envelope before applying it. It reports totals across scenarios and per-scenario counts, and an invalid or cancelled preview leaves the current project unchanged. The canonical boundary accepts the supported legacy aliases (`cableSchedule`, `loadList`, `raceways`, and array or sheet-envelope `oneLine` forms), normalizes them once, and then applies the current schema validation. Unknown ordinary fields and invalid field shapes remain errors. A saved local record may contain `__meta` and synchronization metadata; those fields belong to the storage envelope and are removed before interchange validation. A document with a newer schema version is rejected with an upgrade message.

Browser recovery assumes the application shell and its static modules can load. When the project backend is unavailable, local saved project data can still be loaded, scenarios can be switched, and exports can be generated; the browser journey tests this boundary by blocking `/projects` requests while allowing static assets through. A fully disconnected navigation may instead resolve to the offline fallback page, so that condition is outside the editing and export recovery contract.

Multi-scenario import restores the complete active canonical projection after inactive scenarios are loaded, so active cables, raceways, cable typicals, MCC lineups, and settings cannot be replaced by inactive data. Collaboration snapshots accept the supported legacy storage envelope, normalize it into canonical settings, and persist the canonical envelope so workflow artifacts survive a save and reload.

Local saves and imports report failure when persistent storage rejects any transaction stage, including the final authoritative project write. The previous durable backup remains available while ordinary edits may continue in memory for the current session. Rename uses the current in-memory project snapshot and rolls back the new name if either side of the storage operation fails. The save status preserves both timestamps: when the local timestamp is newer than the cloud timestamp, the compact header says `Local changes` and its detail exposes both times; otherwise it reports the last cloud or local save.

Named-project reloads use the last saved snapshot. Save the active scenario and any completed study before navigating to another page when those results must survive the reload; unsaved scenario changes remain in the current page session.
